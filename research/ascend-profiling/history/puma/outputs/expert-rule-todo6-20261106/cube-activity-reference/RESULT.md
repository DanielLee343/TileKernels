# Cube 活动量除以任务计算量的离线检查

## 本轮结论

已在三份现有 CANN 9.2.0、950PR 卡 6 的单次开发采集上，按原始 `PipeUtilization.csv` 和已登记的矩阵乘合同算出候选描述量。该量值得作为 Cube 规则的候选入口，但当前数据不足以判断异常或设 threshold。三例均属开发试采，并非已确认的专家参考，不能用它们拟合客户规则。

对 FP16 的普通稠密矩阵乘，若该 kernel 覆盖全部矩阵乘计算，可按合同定义名义乘加数 `Q = B × M × N × K`。这里把一次乘加算一个 MAC，报告 FLOP 时沿用每 MAC 两次浮点运算的惯例。`Q` 是合同量，不是硬件实际执行指令或已计数的有效工作。

从同一份 profile 表中取所有 Cube 行的 `aic_cube_time(us)`，求和为 `S`。候选量为 `C = S / Q`，这里用 `μs/GMAC` 表示，越大表示每单位名义计算量对应的累计 Cube 活动时间越多。在同一测量口径下，其倒数可换算为 `2Q/S`，单位为 `TFLOP/s`。两者是同一信息，不能作为两个独立证据叠加。

单纯看到 C 偏大，不能说计算浪费或客户的算子可以提速。尾部填充、矩阵尺寸和形状、输入精度、任务是否全部落在这个 kernel、算子合同中允许的算法、Cube 指令和转换、不同实现的分工，都可能改变这个值。若有 split-K，统计要覆盖全部参与乘法的 Cube 工作，而相加或归约在其他流水上执行的成本不会包含在 S 中。若矩阵乘跨多个 kernel，应同时确认各 kernel 与该次合同的对应和覆盖，当前脚本只读取单个目标，不会自行完成多 kernel 归属。

## 原始合同与复算结果

采集入口按 case 的 `shape` 构造无转置、无 bias 的 `torch.mm` 或 `torch.bmm`，输入和输出 FP16，CPU double 计算参考。三个不同 workload 各只有一次 Default kernel replay，warmup 5，launch count 1，目标都是一条独立识别的 Cube 任务。普通 trace 与 Default 是不同的调用。输出检查是有限值和历史 cosine 门槛，尚未形成逐元素完整精度准入。C1 square 的采集结束时检测到其他设备进程，标记可能干扰。三次均缺整个采集窗口的全机持续独占证据。

| 开发 case | B,M,K,N | Cube 行数 / 活动行数 | S (μs) | Q (MAC) | C (μs/GMAC) | 2Q/S (TFLOP/s) | task duration (μs) |
|---|---:|---:|---:|---:|---:|---:|---:|
| square | 1,256,256,256 | 24 / 24 | 2.482432 | 16,777,216 | 147.9645 | 13.5168 | 3.511 |
| tail | 1,511,768,257 | 25 / 25 | 15.825448 | 100,859,136 | 156.9064 | 12.7464 | 6.896 |
| BMM | 4,128,256,128 | 28 / 24 | 2.482432 | 16,777,216 | 147.9645 | 13.5168 | 3.605 |

square 和 BMM 恰好有相同 Q、相同 S，而矩阵形状、分配行数与 task duration 不同。这一例直接说明 C 不包含全部并行分配、搬运、等待或端到端延迟信息。三个 case 的单次测量不构成跨 shape 参考，tail 比 square 高约 6% 也不足以归因尾块。

## 计量成立条件和当前缺口

1. 数据来自实际目标的 `OpBasicInfo.csv` 和 `PipeUtilization.csv`，同 case 且唯一；行键无重复，表格 Cube 行数与 Block Dim 相等。脚本检查 `cube0`、频率字段 1650 MHz、卡 6、非负有限活动及行内活动时间不大于行时间。BMM 的 4 个零活动行保留计数。行数相等不单独证明 PMU 全部事件有效或每行均有有用工作。
2. `S` 是逐行活动时间之和，单位是累加的 Cube 微秒，不是 task duration。不同 Cube 行可以并行，不能用 S 取代 latency，也不能与 task duration 相加。高或低的 C 单独不能判断关键路径，不能估计提速空间。
3. 本地 `msopprof` 源码在 A5 路径中将 `aic_cube_time(us)` 表达为事件 810 / frequency。但本地源码版本与存档 profiler build `884ac969…` 的完全一致性以及该次配置事件的有效性仍未被独立证明。表中频率为每次记录的 Current Freq 1650 MHz，不等于已经证明整个 replay 中动态频率恒定。当前 C 是按导出字段和标注单位得到的描述，精确硬件语义待认证，不能宣传物理利用率。
4. 数学上 `Q=B×M×N×K` 是传统稠密算法的名义 MAC 数，不能仅从 shape 推断目标 kernel 实际完成了全部 Q。还需确认一次调用覆盖、实际 role、完整输出精度、算法及各侧分工。若算法不是传统稠密乘加或存在稀疏、预处理与重算，先重新定义合同 Q。活动时间还可能含填充及重复计算，但没有逐指令工作量和有效性证据时无法拆分。
5. 复采应按 case 等权，复采只用于测量波动，不能充作独立专家或独立 case。时钟、硬件、CANN / profiler、计数口径和预热/replay/L2 条件须匹配，跨平台不得沿用 threshold。

## 后续最小实验

先核验现有 C3 确定性 Cube 对照里活动时间字段及运行条件。C3 并未改变乘法工作，适合作为字段稳定性和重复性的一条控制线索，不能靠它单独证明事件完整或认证所有 dtype、形状的活动计数。如果出现显著偏离，先查测量窗口、实际频率或采集竞争。

在不影响 C3 的前提下，用已经准备的 `c1-exact` 同一 [256,256] FP16 输入合同，比较 CANN 和独立 Triton 实现。先验收完整输出、目标任务数量、格式、设备与采集合同，再交错重复同一调用和采集。两实现未必都是单 Cube kernel，必须检查角色与归属。该对照用来检验 C 能否在相同必要计算量下区分执行情况，较快实现能否作为该 case 专家需同合同、同设备、同方法及稳定性能证据。

随后从符合首版范围的专家实现中预登记不同 M/N/K、batch、尾块、dtype 等多个 case，保留未用于选择关系的独立专家任务。可先比较简单的常数 C 假设，再检查形状、dtype、尾块等是否形成系统残差；连续条件保持连续，数据不足的区域返回参考不足。仅在适用条件与模型固定后使用独立专家校准数值边界，并独立检查覆盖与误报。无需假设所有专家共享一个阈值，也不预设 C 一定能提供有效报警。
